## About

A complete URL shortening service built end to end: a **FastAPI** backend,
**Supabase** (PostgreSQL) for persistence, a **vanilla HTML/CSS/JavaScript**
frontend, and **automated deployment** through GitHub Actions.

One server delivers both the site and the API — a single origin, no CORS in
production.

> Note: the codebase and inline comments are written in Portuguese.

## Features

- **Shortening** — 7-character codes generated with `secrets` (cryptographic randomness, not `random`)
- **Redirection** — `GET /{code}` sends the visitor to the original URL
- **Click counting** — every visit increments the counter in the database
- **Collision handling** — if a generated code already exists, another is drawn automatically
- **URL validation** — through Pydantic's `HttpUrl`, rejecting invalid input with a 422
- **Copy to clipboard** — one click, with visual feedback
- **Loading and error states** — a specific message for each possible failure
- **Responsive, accessible UI** — semantic HTML, visible focus rings, `aria-live` announcements

## Stack

| Layer | Technology | Why |
|---|---|---|
| **API** | FastAPI + Uvicorn | Automatic validation from type hints, OpenAPI docs for free |
| **Database** | Supabase (PostgreSQL) | Managed Postgres, no server to maintain |
| **Frontend** | HTML + CSS + JS (ES Modules) | No framework, no build step — the goal was to master the fundamentals |
| **Tests** | pytest | 7 tests, all isolated from the real database |
| **CI/CD** | GitHub Actions | Tests on every push; deploy only if they pass |
| **Hosting** | Render | Continuous deployment via webhook |

## How it works

```
  ┌──────────────┐
  │   BROWSER    │
  └──────┬───────┘
         │  1. POST /encurtar   { "url_original": "https://some-very-long-site.com/..." }
         ▼
  ┌─────────────────────────────────┐
  │   FASTAPI  (Render)             │
  │                                 │     2. INSERT  { code, original_url }
  │   • validates the URL (Pydantic)│ ──────────────────────────────►┌────────────┐
  │   • draws a code (secrets)      │                                │  SUPABASE  │
  │   • builds the short URL        │ ◄──────────────────────────────│ PostgreSQL │
  └─────────────────────────────────┘     3. ok                      └────────────┘
         │
         │  4. { "url_curta": "https://encurtaa.onrender.com/aB3xY9k" }
         ▼
  ┌──────────────┐
  │   BROWSER    │  shows the link + copy button
  └──────────────┘


  Later, when someone opens the short link:

  GET /aB3xY9k  ──►  FastAPI  ──►  SELECT url_original WHERE codigo='aB3xY9k'
                                   UPDATE qtd_cliques = qtd_cliques + 1
                        │
                        └──►  HTTP 307 Redirect  ──►  original site
```

## Running locally

Requirements: **Python 3.12+** and a free [Supabase](https://supabase.com) account.

### 1. Clone the repository

```bash
git clone https://github.com/thainaoliv/EncurtaA-.git
cd EncurtaA-
```

### 2. Create a virtual environment

A virtual environment isolates this project's libraries from the rest of the
machine, so a version installed here cannot break another project.

```bash
python -m venv .venv

# Windows (PowerShell)
.venv\Scripts\Activate.ps1

# Linux / macOS
source .venv/bin/activate
```

### 3. Install dependencies

```bash
pip install -r backend/requirements.txt
```

### 4. Set up the database

In the Supabase dashboard, create the `links` table (**SQL Editor → New query**):

```sql
create table links (
  id           bigint generated by default as identity primary key,
  codigo       text   not null unique,
  url_original text   not null,
  qtd_cliques  int    not null default 0,
  criado_em    timestamptz default now()
);
```

> The `unique` constraint on `codigo` is not decoration: it is what guarantees two
> links never share a code. The backend relies on that database error to detect
> collisions.

### 5. Configure environment variables

Create `backend/.env`:

```env
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_KEY=your-anon-key
BASE_URL=http://127.0.0.1:8000
ALLOWED_ORIGINS=http://localhost:5500,http://127.0.0.1:5500
```

Find `SUPABASE_URL` and `SUPABASE_KEY` under **Settings → API** in Supabase.

> ⚠️ `SUPABASE_URL` is the **database** address (`...supabase.co`), not the address
> where the app is hosted. Swapping the two makes the backend send its queries to
> itself and answer 500.

`.env` is listed in `.gitignore`: **credentials never reach the repository.**

### 6. Start the server

```bash
cd backend
uvicorn api:app --reload
```

That's it:

| Address | What it is |
|---|---|
| http://127.0.0.1:8000 | the site |
| http://127.0.0.1:8000/docs | interactive API documentation (Swagger) |

## Tests

```bash
cd backend
python -m pytest -v
```

```
7 passed
```

The suite covers code generation (1,000 iterations checking length and alphabet),
lookups for existing and missing links, click counting, the happy path of creation,
**collision handling**, and **real-error propagation**.

None of them touch a real database: each injects a stand-in for the Supabase client
through `monkeypatch`. They run offline, in under a second, and never pollute real
data.

## API

| Method | Route | Description | Response |
|---|---|---|---|
| `GET` | `/` | Home page | HTML |
| `POST` | `/encurtar` | Creates a short link | `{ "url_curta": "..." }` |
| `GET` | `/{code}` | Redirects to the original URL | `307` or `404` |
| `GET` | `/docs` | OpenAPI documentation | HTML |

```bash
curl -X POST https://encurtaa.onrender.com/encurtar \
  -H "Content-Type: application/json" \
  -d '{"url_original": "https://github.com"}'

# {"url_curta":"https://encurtaa.onrender.com/aB3xY9k"}
```

## Deployment pipeline

Defined in [`.github/workflows/ci.yml`](.github/workflows/ci.yml):

```
git push
   │
   ├─► install Python and dependencies
   ├─► run the 7 tests  ──── failed? ──► stop here, no deploy
   │                                     (production stays untouched)
   └─► passed? ──► trigger the Render deploy hook ──► site updated
```

The key point: **deployment only happens if the tests pass.** Broken code never
reaches production.

## Architecture decisions

Some choices here were deliberate. The reasoning is worth spelling out:

<details>
<summary><strong>The backend builds the short URL, not the frontend</strong></summary>

<br>

`criar_link()` returns **only the code** (`aB3xY9k`); `api.py` assembles the full
URL using the `BASE_URL` environment variable.

Letting the frontend concatenate `location.origin + "/" + code` would have been
easier — but then the public address would be defined in two places, and two places
drift apart. The rule adopted: **one owner per piece of information.** The backend
knows which address it runs on, so the backend answers that question.

Useful side effect: the API serves any client (a mobile app, a CLI, another
service), not just this site.

</details>

<details>
<summary><strong>Code collisions are handled, not ignored</strong></summary>

<br>

With 62 possible characters across 7 positions there are ~3.5 trillion
combinations — a collision is unlikely, but unlikely is not impossible.

Rather than checking first ("does this code already exist?"), the code attempts the
insert and handles the database error:

```python
except Exception as erro:
    if "duplicate key" in str(erro):
        continue        # draw another one and retry
    else:
        raise           # a genuine error: do not swallow it
```

Checking first would introduce a *race condition*: between the check and the
insert, another request could write the same code. The database's `unique`
constraint is the only genuinely atomic check. And the `else: raise` is essential —
an `except` that swallows everything turns a connection failure into a silent bug.

</details>

<details>
<summary><strong>Tests use a stand-in instead of the real database</strong></summary>

<br>

Each test replaces the Supabase client with a fake class via `monkeypatch`. More
work to write, but:

- they run **offline**, in under a second
- they never pollute the database with test junk
- they test **my** code, not Supabase's availability
- the collision test becomes possible at all — forcing a real collision is
  infeasible, but a stand-in can raise `duplicate key` on the first call and
  succeed on the second

</details>

<details>
<summary><strong>One server delivers both the site and the API</strong></summary>

<br>

FastAPI serves `index.html` at the root and mounts the `css/`, `js/` and `assets/`
folders. Same origin for site and API means **no CORS problems in production** and a
single service to host.

The route order in the file is intentional: `GET /{codigo}` comes **last**, because
it is a wildcard matching any single-segment path. Declared earlier, it would steal
requests from the specific routes.

</details>

<details>
<summary><strong>CSS files are numbered</strong></summary>

<br>

```
01-reset.css  →  02-tokens.css  →  03-base.css  →  04-layout.css  →  05-components.css
```

CSS is a cascade: when specificity ties, **whatever comes later wins**. Numbering
makes that dependency explicit in the filesystem instead of hiding it in the order
of `<link>` tags. From the most generic (reset) to the most specific (components).

</details>

<details>
<summary><strong>No frontend framework</strong></summary>

<br>

React would have solved this in fewer lines. But the point of the project was to
understand the fundamentals: DOM manipulation, `fetch`, `async/await`, ES Modules,
form events and the CSS cascade — with no abstraction layer hiding how any of it
works.

The code is still organised into single-responsibility modules: `api.js`
(communication), `clipboard.js` (copying), `main.js` (orchestration and DOM).

</details>
